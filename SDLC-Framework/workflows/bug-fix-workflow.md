# Bug 修复工作流

> **基于 SDD 反馈循环的 Bug 修复流程**

本文档描述如何使用 SDLC Framework 修复 Bug，并从每个 Bug 中学习改进框架。

---

## 工作流概览

```
Bug 报告 → 复现定位 → 框架反思 → 修复实现 → 验证关闭 → 框架更新
```

**核心原则**: 不要只修 Bug，要思考框架改进

---

## 阶段详解

### 阶段 1: Bug 报告接收

**输入**: Bug 报告（Jira/GitHub Issue/用户反馈）
**输出**: 标准化的 Bug 记录

**活动**:
1. 确认 Bug 有效性
2. 评估影响范围和严重程度
3. 分配优先级
4. 创建 Bug 跟踪记录

**命令示例**:
```bash
# 从 Jira 导入 Bug
/bug-fix --from-jira=BUG-123

# 手动创建 Bug 记录
/bug-fix --create "登录页面在移动端显示异常"
```

---

### 阶段 2: 问题复现与定位

**输入**: Bug 报告
**输出**: Bug 根因分析

**活动**:
1. 在本地复现问题
2. 定位问题代码位置
3. 分析触发条件
4. 记录复现步骤

**分析模板**:
```markdown
## Bug 分析

**现象**: [描述 Bug 表现]

**复现步骤**:
1. 步骤一
2. 步骤二
3. ...

**定位结果**:
- 文件: [文件路径]
- 行号: [行号范围]
- 相关代码: [代码片段]

**根因**: [描述根本原因]
```

---

### 阶段 3: 框架反思 ⭐ 关键步骤

**这是 SDD 方法论的核心**: 每个 Bug 都是对框架的一次反馈机会。

**输入**: Bug 根因分析
**输出**: 框架改进建议

**活动**:

#### 3.1 判断缺口类型

| 类型 | 特征 | 示例 |
|------|------|------|
| **A: 规范→实现** | 规范写清楚了，实现跑偏 | 需求说"必填"，代码没校验 |
| **B: 意图→规范** | 需求讨论时漏了细节 | 没考虑移动端适配 |
| **C: 角色协作** | 角色间信息传递丢失 | 前端不知道后端改了接口 |

#### 3.2 记录反思

使用模板记录: `guidance/feedback/templates/BUG-REFLECTION.md`

```markdown
## 框架反思

### 缺口类型
- [x] B: 意图→规范缺口

### 根因分析
需求收集时没有考虑移动端场景，响应式设计规范缺失。

### 改进措施
- [ ] 在产品设计阶段添加"多端适配检查清单"
- [ ] 更新 UI 流程模板，增加移动端流程图
- [ ] 添加前端开发规范中的响应式设计要求
```

#### 3.3 更新指导文档

根据缺口类型，更新对应的指导文档：

| 缺口类型 | 更新文档 |
|----------|----------|
| A: 规范→实现 | 质量门禁、检查清单 |
| B: 意图→规范 | 需求模板、引导问题 |
| C: 角色协作 | 角色职责、交接检查点 |

---

### 阶段 4: 修复实现

**输入**: Bug 分析 + 框架反思
**输出**: 修复代码

**活动**:
1. 创建修复分支
2. 编写失败的测试用例（可选）
3. 实现修复代码
4. 确保所有测试通过

**Git 工作流**:
```bash
# 创建修复分支
./SDLC-Framework/scripts/start-feature.sh fix-login-mobile

# 实现修复
# ... 编写代码 ...

# 提交修复
git add .
git commit -m "fix(auth): 修复移动端登录页面显示异常

- 修复响应式布局问题
- 添加移动端适配测试

Closes #123

Framework-Feedback: 添加移动端适配检查清单到产品设计阶段"

# 推送并创建 PR
./SDLC-Framework/scripts/finish-feature.sh
```

---

### 阶段 5: 验证与关闭

**输入**: 修复代码
**输出**: 验证通过的修复

**活动**:
1. 代码审查
2. 测试验证
3. 回归测试
4. 关闭 Bug 记录

**验证检查清单**:
- [ ] Bug 已复现并确认修复
- [ ] 单元测试已添加/更新
- [ ] 无回归问题
- [ ] 代码审查通过
- [ ] 相关文档已更新

---

### 阶段 6: 框架更新

**输入**: 框架反思记录
**输出**: 更新后的框架文档

**活动**:
1. 更新 `guidance/CONSTITUTION.md` 或相关 Steering Doc
2. 更新相关模板
3. 在 `guidance/feedback/FRAMEWORK-FEEDBACK.md` 中记录
4. 提交框架更新

**示例更新**:

```markdown
<!-- 在 guidance/CONSTITUTION.md 中添加 -->

### 前端开发规范

- [ ] **响应式设计**: 所有 UI 必须支持移动端适配
- [ ] **多端测试**: 核心功能必须在移动端测试通过
```

## 快速命令参考

```bash
# 完整 Bug 修复流程
/bug-fix --ticket=BUG-123

# 从 Jira 导入
/bug-fix --from-jira=BUG-456

# 只做框架反思（不修代码）
/bug-reflect --ticket=BUG-123

# 查看框架反馈统计
/bug-stats
```

---

## 质量门禁

每个 Bug 修复必须通过以下检查：

### 修复前
- [ ] Bug 已复现
- [ ] 根因已定位
- [ ] **框架反思已完成** ⭐

### 修复后
- [ ] 修复代码已提交
- [ ] 测试通过
- [ ] 代码审查通过

### 关闭前
- [ ] 验证通过
- [ ] **指导文档已更新** ⭐
- [ ] 反馈记录已归档

---

## 与 SDD 的对应关系

| SDD 概念 | 本工作流实现 |
|----------|--------------|
| 规范是唯一入口 | Bug 修复前先反思规范缺口 |
| 反馈循环 | 阶段 3 + 阶段 6 |
| 缺口分类 | A/B/C 三种缺口类型 |
| 框架强化 | 每个Bug都用来改进框架 |
