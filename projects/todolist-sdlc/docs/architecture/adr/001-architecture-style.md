# ADR-001: 选择单体架构而非微服务

## 状态

已接受

## 日期

2026-03-16

## 背景

TodoList 项目需要添加任务标签功能，需要决定架构风格：单体架构还是微服务架构。

## 决策

**采用单体分层架构**

## 理由

| 考虑因素 | 单体架构 | 微服务架构 | 选择 |
|----------|----------|------------|------|
| 团队规模 | 小型团队 | 需要 DevOps 团队 | ✅ 单体 |
| 功能复杂度 | 简单到中等 | 复杂业务域 | ✅ 单体 |
| 部署成本 | 低 | 高（容器编排） | ✅ 单体 |
| 开发速度 | 快 | 慢（服务间通信） | ✅ 单体 |
| 扩展需求 | 垂直扩展足够 | 水平扩展需求 | ✅ 单体 |
| 事务一致性 | 简单（ACID） | 复杂（分布式事务） | ✅ 单体 |

## 后果

### 正面

- 开发速度快，团队可以专注业务功能
- 部署简单，一个 JAR 包即可
- 事务处理简单，无需分布式事务
- 调试和监控更容易

### 负面

- 未来扩展需要重构
- 单点故障风险（可通过负载均衡缓解）

## 替代方案

### 方案 A: 微服务架构

- **优点**：独立扩展、技术栈灵活
- **缺点**：运维复杂、分布式事务、开发速度慢
- **拒绝理由**：当前规模不需要，团队资源有限

### 方案 B: 模块化单体

- **优点**：保持单体优势，模块边界清晰
- **缺点**：需要良好的模块化实践
- **未来考虑**：如果项目增长，可迁移到此方案
